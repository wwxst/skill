# Reporting — 面向开发者的执行过程与结果汇报

本文件每次审查都必须读取。目标是让开发者清楚知道 AI 实际做了什么，而不是只看到一句“审查通过”。

## 1. 汇报原则

报告必须回答：
1. 主 Agent 做了什么？
2. 实际创建了哪些子 Agent？每个 Agent 负责什么？
3. 每个 Agent 实际检查了哪些内容、读取了哪些规则？
4. Agent 之间如何沟通？采用直接消息还是主 Agent 中转？讨论了哪些问题、如何回应？
5. 每个 Agent 发现了什么？哪些问题被独立验证为真，哪些被排除？
5. 确认的问题如何修复？修改了哪些文件？
6. 修复后运行了什么测试？结果如何？
7. 最终还有什么风险或需要开发者决定的事项？

报告使用简洁、直白的中文。不要只给 Agent 数量，也不要把所有子 Agent 的原始输出原封不动堆给开发者。

不输出模型私有思维链或内部推理过程。应汇报可审计的行动、输入范围、证据、结论和执行结果。

## 2. 第一部分：总体结论

报告开头先给：
- 最终状态；
- 审查范围；
- 风险等级；
- 实际创建并完成的 Agent 数量；
- 发现的问题数量；
- 修复数量；
- 测试通过/失败数量；
- 是否需要开发者处理。

如果没有真实创建子 Agent，必须在开头醒目标注：
`未执行多 Agent 审查：当前环境不具备所需能力。`
并说明是否已征得开发者同意采用单 Agent 降级。

## 3. 第二部分：主 Agent 做了什么

用时间顺序或步骤概述：
- 检查了哪个分支、提交和 diff；
- 读取了哪些项目规则和 Skill 文件；
- 检查了哪些运行环境能力；
- 执行了哪些基础测试；
- 创建了哪些 Agent；
- 如何收集和验证结果；
- 如何决定修复、复审和结束。

只记录真实执行过的内容。计划但未执行的步骤要明确标注未执行及原因。

## 4. 第三部分：Agent 之间如何沟通

必须写明：
- 沟通模式：`DIRECT`、`COORDINATOR_RELAY` 或 `NOT AVAILABLE`；
- 哪些 Agent 互相交换了哪些 Finding；
- 谁提出质疑、补充证据或反例；
- 对方如何回应；
- 哪些结论因此被修改、保留或撤销；
- 哪些分歧仍未解决。

如果没有沟通能力，写明已告知开发者，以及开发者是否同意受限模式。

## 5. 第四部分：子 Agent 工作清单

每个 Agent 单独一行或一个小节，至少记录：

| 字段 | 内容 |
|---|---|
| Agent 名称 / ID | 宿主实际返回的名称或任务 ID |
| 角色 | Bug Hunter A / B / C、Voter、Security Reviewer、Fix Agent 等 |
| 创建状态 | 成功 / 失败 / 未启动 |
| 执行状态 | 完成 / 失败 / 超时 / 取消 |
| 任务范围 | 实际检查的 diff、文件或模块 |
| 读取规则 | 实际读取的 Skill 参考文件和项目规则 |
| 工作结果 | 检查了什么，发现多少候选问题 |
| 关键结论 | 重要发现、排除理由或未能完成的事项 |

如果 Agent 失败、超时或未启动，说明原因。不能把它算作完成。

## 6. 第五部分：问题处理过程

对每条确认问题建立处理链：

`发现 Agent → 独立 Voter → 主 Agent 确认 → 修复者 → 回归测试 → 最终状态`

示例字段：
- Finding ID；
- 谁首先发现；
- 哪些 Voter 确认或否定；
- 问题证据和触发条件；
- 是否由本次变更引入；
- 谁执行修复；
- 修改了哪些文件；
- 运行了什么回归测试；
- 最终状态：已修复 / 已接受风险 / 未解决 / 误报。

不能只说“已修复”，要说清楚修复了什么，以及用什么验证。

## 7. 第六部分：测试和验证

用表格列出真实运行过的检查：
- 命令；
- 检查目的；
- 结果；
- 失败原因或关键输出。

状态只允许：
- `PASS`
- `FAIL`
- `NOT RUN`
- `BLOCKED`

不得把未运行说成通过。

## 8. 第七部分：剩余风险和开发者需要知道的事

明确列出：
- 未解决的 finding；
- 证据不足的 UNCERTAIN 项；
- 未完成或失败的 Agent 任务；
- 未运行的测试；
- 需要开发者决定的产品或架构取舍；
- 不能由 Skill 自身保证的外部动作（如 CI 分支保护、部署、回滚）。

如果没有剩余事项，明确写“没有发现需要开发者额外处理的事项”。

## 9. 汇报详细程度

报告要让开发者看懂，但不要变成几千行日志：
- 总览：简短；
- Agent 清单：每个 Agent 说明职责、检查范围和结果；
- Finding：只展开真实问题；
- 测试：列出命令和状态；
- 原始 Agent 输出：仅在开发者要求时附上。

主 Agent 必须把分散的子 Agent 结果整理成一份完整报告，不能要求开发者自己逐个翻 Agent 会话。


## 10. Agent 执行账本必须出现在最终报告

最终报告必须包含一张执行账本，不能只写“创建了 11 个 Agent”。

至少包含：

| Agent ID | 角色 | 状态 | 候选问题数 | 交叉沟通 | 投票/验证 | 最终贡献 |
|---|---|---|---:|---|---|---|
|  |  |  |  |  |  |  |

要求：
- 每一行都对应真实创建的 Agent。
- 总数由表格行数和状态汇总。
- 如果平台没有 Agent ID，明确写“平台未提供”。
- 不能把未创建的角色写进去凑数量。
- 如果 Agent 失败、超时或未返回，必须显示真实状态。

## 11. Finding 来源账本

每条 finding 必须能回答“从哪里来的”。

| Finding ID | 首次来源 | 阶段 | 是否交叉质疑 | Voter 结果 | 最终状态 |
|---|---|---|---|---|---|
| F-001 | Agent A | 首轮 Bug Hunt | 是 | CONFIRMED | 已修复 |

如果交叉讨论新增一条 finding，必须写：
- 提出者；
- 发生在哪次沟通；
- 依据什么代码证据；
- 为什么首轮没有发现。

这样候选总数必须能逐条相加，不允许出现“10 条 + 3 条最后变成 14 条却没说明”的情况。

## 12. 流程异常必须透明记录

单独增加“流程异常”一节，记录：
- 提前引用尚未返回 Agent 的结论；
- Agent 启动失败、超时、取消；
- 结果回收失败；
- Agent 数量与报告数量不一致；
- finding 数量无法追溯；
- 误把受限模式写成完整多 Agent 模式；
- 未经授权执行 Git 写操作；
- 其他影响审查可信度的异常。

每项写清：
- 发生了什么；
- 影响什么；
- 是否已纠正；
- 是否影响最终结论。

没有异常时明确写“无流程异常”。

## 13. Review Only 的 Git 行为必须汇报

Review Only 模式下必须写：
- Git 写操作：`0`
- 是否执行 commit：否
- 是否执行 push：否
- 是否创建 PR：否

如果这些任何一项为“是”，必须给出用户明确授权来源；没有授权则标记流程违规。
