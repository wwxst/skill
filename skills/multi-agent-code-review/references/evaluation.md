# Reviewer Evaluation — 历史问题评测与持续改进

## 1. 建立历史缺陷评测集

使用真实案例：
- 导致事故的历史 PR；
- 后续修复提交；
- Revert PR；
- 由熟悉代码的人确认过的问题和准确位置。

每个案例记录：
- 原始变更；
- 实际 Bug；
- 文件和行号；
- 触发条件；
- 实际影响；
- 正确修复；
- 评测标签。

## 2. 同时衡量发现率和误报率

跟踪每条审查评论最终：
- 被修复；
- 被证明是错误发现；
- 行为本来就是有意设计；
- 问题存在但影响不值得处理。

也要用已知干净的 PR 测试 Reviewer 是否提出错误意见，尤其是会诱导开发者做有害修改的建议。

优先级：
1. 真实 Bug 发现能力；
2. 误报控制；
3. 审查耗时和 Token 成本。

不能只用“发现了多少问题”评价质量。

## 3. 重复问题修在源头

如果某类问题反复出现，判断应该修正：
- `REVIEW.md`：项目专属审查规则；
- `CLAUDE.md`：项目技术栈、约定和目标；
- Skill：可复用的审查流程；
- Lint / 静态检查：适合程序确定性检查的规则；
- 测试：需要自动防止回归的行为。

## 4. 定期扫描已有代码

可以额外执行 Nightly Review，对已有代码做 Bug Hunt。

定期扫描结果应与当前 PR 审查分开，不能把历史问题归咎于当前变更。
