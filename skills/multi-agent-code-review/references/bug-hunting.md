# Bug Hunting — Bug Hunter 审查规则

所有 Bug Hunter 必须读取本文件。

## 1. 审查目标

找出本次变更引入或扩大的真实问题，而不是尽可能多地发表评论。

审查时同时考虑：
- 本次 diff；
- 原始需求和验收标准；
- 整个仓库中相关实现；
- 调用方、被调用方、接口和数据结构；
- 项目规则和架构约束。

## 2. 必须检查的维度

### 行为正确性与根因
- 修改是否真正满足需求；
- 正常路径是否正确；
- 是否存在错误分支、状态转换错误；
- Bug 修复是否修复根因，而不是绕过表面症状；
- 是否破坏已有行为或兼容性。

### 集成与数据流
- 上下游调用链是否正确；
- API、事件、配置、持久化和数据结构是否一致；
- 是否破坏模块职责和依赖方向；
- 是否存在竞态、资源泄漏或状态不一致；
- 是否影响其他调用方。

### 边界和失败路径
- 空值、无效输入和极端值；
- 异常、超时、取消和重试；
- 文件、网络和权限边界；
- 失败后的恢复行为；
- 幂等性和重复执行；
- 测试是否遗漏关键失败路径。

## 3. 问题成立的最低证据要求

每个候选问题必须说明：
1. 哪段代码存在问题；
2. 具体触发条件；
3. 程序会出现什么错误行为；
4. 对用户、数据或系统有什么实际影响；
5. 为什么问题由本次变更引入或扩大；
6. 建议如何修复。

缺少触发条件或实际影响的意见，不应作为确认问题提交。

## 4. 不应报告的内容

不要报告：
- 纯格式和排版；
- 个人命名偏好；
- 没有行为影响的风格差异；
- 与本次变更无关的重构；
- 仅仅“可以更优雅”的建议；
- 没有代码证据的理论猜测；
- 已经报告且代码没有变化的问题。

`Nit` 必须是真实、低影响、可操作的问题，不是风格评论。

## 5. 输出格式

每个 Bug Hunter 独立返回：

```text
Agent:
Role:
Review Scope:
Status: COMPLETED / FAILED

Candidate Findings:
- ID:
  Title:
  Category:
  Severity: CRITICAL / HIGH / MEDIUM / LOW
  File:
  Line:
  Evidence:
  Trigger:
  Actual Impact:
  Introduced By This Change: YES / NO / UNCERTAIN
  Suggested Fix:
  Confidence: HIGH / MEDIUM / LOW

If no findings:
0 个候选问题。

Notes:
未检查的区域、无法验证的假设和工具限制。
```

只读审查，不修改文件，不与其他审查 Agent 交换结论。
